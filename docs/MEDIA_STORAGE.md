# 图片上传、审核与恢复

世界支持实际上传 JPEG/PNG。文件由 Go 校验并重编码，元数据存入 PostgreSQL，图片存放在专用私有目录。它是当前可运行的自托管存储；尚未接入 S3、CDN、视频转码或外部识别服务。

## 体验完整链路

1. 使用成员示例登录，进入「发现 → 世界 → ＋」，选择最多9张图片。每张图有排队、上传、成功或失败状态；失败可用同一请求重试，上传不会自动发布。
2. 填入文字并发布。使用托管图片的帖子先进入待审核，发布器给出真实详情链接；作者能看到图片和状态，访客暂不可读。
3. 使用另一个浏览器登录运营后台，在「内容审核」打开待审帖子并发布。公开世界和图片访问随审核结果开放。
4. 后台「图片管理」可按图片、用户或引用帖子搜索，查看原图、尺寸、大小与引用，并填写说明屏蔽图片。已发布引用帖会同时隐藏；解除屏蔽后，还需单独审核帖子。
5. 「账号 → 我的上传」可以找回取消或超时后实际已保存的图片。没有帖子引用时可以确认删除；已有引用需先删除相关帖子。圈内引用提供「删除圈帖」，确认会删除整篇本人帖子，成功后重新读取引用，原图仍保留；即使作者已退出或被移除，也能清理自己的引用。失败保留状态并可重试，403/404可刷新引用。已屏蔽图片不在普通用户端显示原图。

站内通知会告知图片真实审核状态变化，以及屏蔽造成的帖子隐藏结果；同状态只改说明不刷通知，内部note不进入通知。图片通知打开 `/account/uploads?image=media_<32小写hex>`，按当前账号定位对应未删资产；未知/他人ID不会显示旧卡片，切换目标或账号会清除旧请求结果。它不是公开原图链接，屏蔽图仍不发普通端图片请求。完整事件与权限见 [通知服务](NOTIFICATIONS_SERVICE.md)。

`npm run verify:media` 会走真实 Vite/API/数据库流程，并在成员示例账号保留一篇已发布图片示例和一篇待审示例。图片是明确标注的渐变测试图，便于直接体验审核，不冒充用户照片。脚本仅接受本机开发端口，不对生产执行，报告位于 Git 忽略的 `.runtime/verify-media-result.json`，不含 Cookie 或口令。

## 圈内图片

圈子从自己的发布器上传，资产创建时固定为circle作用域并绑定一个圈子。世界上传仍是world作用域；既不能把圈图发往世界，也不能跨圈引用。圈内图帖先待审，发布后只有当前有频道权限的圈成员可读取原图，圈子本身公开也不改变这一规则。被移除、退出或降级后，每次读取重新鉴权；平台暂停圈后，其他成员无法继续读取圈内图片。

上传者可在「我的上传」找回本人图片。界面与后台分别显示世界公开引用和圈内引用，删除要求两边引用全部解除。作者删除自己的圈帖仅解除该帖引用，不恢复圈内阅读权；归档圈/频道和失去成员身份也不阻止这项本人清理。成功删除保留帖子clientId墓碑，重复发布不能复活。屏蔽原图同时隐藏两域已发布引用帖，解除屏蔽不会自动发布。数据库与图片仍按下述完整bundle共同备份，circle作用域、通知与权限元数据包含在数据库dump中。完整接口见 [圈子服务说明](CIRCLES_SERVICE.md)。

## 文件与权限

`dev:all` 默认使用项目 `.runtime/media`。单独运行 Go 时可以设置 `MEDIA_DIRECTORY` 为专用绝对路径。目录必须真实存在为私有目录，或由应用新建为0700；配置共享目录、根目录、符号链接或无法安全写入时启动失败，不替操作者修改已有共享目录权限。文件使用随机ID与固定扩展名，以0600写入，不保存原文件名。

生产配置必须明确提供目录；Compose 使用 `/var/lib/gongming/media` 与 `media-data` 持久卷，API非root、根文件系统只读，只有媒体卷可写。多实例需要访问同一可靠的媒体存储；本机目录和单实例并发限制不等于跨实例存储、分布式限流或生产容量保证。

服务端读取实际图片格式、限制文件与像素、按 JPEG 方向信息变换像素后重新编码，丢弃原始EXIF等元数据；不将原始输入直接提供给浏览器。方向解析仅检查有界 IFD0 Orientation，不跟随缩略图或递归指针。实现依据 [CIPA Exif 2.3](https://www.cipa.jp/std/documents/e/DC-008-2012_E.pdf)，文件访问使用 Go 的 [os.Root](https://go.dev/blog/osroot) 及固定文件名。

图片读取每次检查当前会话、资产状态和已发布引用，PostgreSQL路径仅查所需表，不加载全域State。上传、配额、引用和审核元数据使用数据库事务与约束；管理端点仍有State读取边界。缓存为no-store，已下载到用户设备的内容不能事后抹除。

## 故障与清理

文件系统和 PostgreSQL 不共享事务。文件先以独占随机名称写入、同步文件及目录，再提交元数据；明确业务拒绝可清理候选。遇到未知数据库/提交结果，保守保留文件，避免删除可能已经提交的图片。逻辑删除先提交，再清文件；清理失败会留下不可读取的文件。

因此磁盘上可能存在无元数据或已软删的残留文件，需要后续离线核对和清理。当前备份只包含未删除且有元数据的有效文件，并拒绝软链、硬链接或特殊节点；不能据此认为所有残留都已自动清除。对象存储生命周期、缩略图、去重、自动孤儿清理与监控仍需继续交付。

## 一致性备份与隔离恢复

`db:backup` 只备份数据库，不能独自恢复图片。已有图片后应使用媒体bundle：停掉全部应用写入实例，保留数据库运行，再执行：

```sh
APP_ENV=development npm run media:backup -- --writers-stopped
APP_ENV=development npm run media:restore-check -- /绝对路径/媒体备份目录 --writers-stopped
```

工具只允许显式开发环境、本机项目55432库及安全库名。它探测配置的 API 端口已停止；`--writers-stopped` 仍是操作者对全部实例停写的声明，不能自动证明其它机器或其它端口没有写入。

备份保留数据库只读导出快照，`pg_dump --snapshot` 与媒体元数据来自同一快照；在专用私有bundle中保存dump、有效文件和SHA-256/大小清单，复制前后检查源文件和最终资产集合。恢复演练先校验清单与文件，再创建全新临时数据库和目录，恢复并核对元数据与文件，最后只清理自己新建的演练资源；不会覆盖运行库。

真实恢复上线仍需操作者在停服后将经过演练的数据库和图片作为同一检查点切换，不能混用不同时间的备份。生产卷备份、加密、异地保留、恢复权限及故障演练需要部署环境独立验证；这里的开发工具不声称已覆盖生产灾备。
